# Q2E exact-context prefill/decode benchmark

## Result

The current Q2E direct-slot implementation completed a single-boot exact-token
sweep at 16K, 80K, 160K, and 240K. Every measured cell returned the two target
codes in order, emitted exactly 256 output tokens, covered all 12 QSA layers,
kept CPU round-trip checks exact, and stayed within the unchanged 4,160-page
GPU ownership cap.

## Measurement contract

The engine was loaded once with `max_model_len=246000`. A 4K request warmed
the JIT and allocator, after which the four measured requests ran in increasing
context order without restarting vLLM. Prefix caching was disabled. At the
start of each request the Q2E worker observed position zero and rebuilt its CPU
backing, LRU state, dynamic READ table, and counters; scheduler ownership was
released by request ID. This avoids both repeated model load and cross-cell KV
reuse.

All cells used:

- exact token-ID prompts generated by the KVMEM turn builder;
- direct CPU-to-QSA-slot I/O with the proven consumer synchronization barrier;
- 16-token QSA pages, 128 WRITE pages, 4,032 READ pages, and 64-row dynamic
  splitting;
- `gpu_memory_utilization=0.92`, scheduler chunk 1,024, eager mode, MTP off;
- 256 requested output tokens with `ignore_eos=true` so every decode
  denominator is identical;
- Q2E qualification trace disabled, while worker and scheduler capacity
  evidence remained enabled.

Prefill time is client-observed TTFT: request submission through receipt of the
first streamed output token. Prefill throughput is API prompt tokens divided by
TTFT. Decode excludes the first output token: `(completion_tokens - 1) /
(request_wall - TTFT)`. These are loopback end-to-end service measurements,
not kernel-only timings and not the internal `prefill_exposed` metric used in
earlier profiling.

The compact machine-readable result is
`docs/evidence/R1_KVMEM_Q2E_CONTEXT_BENCHMARK_61A8EB2.json`. Full worker and
scheduler JSONL, response bodies, engine log, generated exact-token cases, GPU


The first attempt stopped before engine boot because a discarded 240K sticky
source plan overlapped the generated active suffix. The benchmark plan builder
was corrected to derive only the Q2D-required fields directly from the exact
case. The second attempt stopped after warmup because a 16-token warmup was
incorrectly subject to the full-answer semantic gate. No measured cells were
produced by either attempt. The final run keeps warmup outside that semantic
gate while retaining it for all four measured cells.

This is one sample per context, so it establishes a current performance curve,
not run-to-run variance. Forced continuation after EOS can produce meaningless
text after the correct answer; it is deliberate here to hold the decode
denominator at exactly 255 timed tokens. Decode is the current no-MTP Q2E path
and should not be compared directly with earlier k=3 speculative-decoding
tables.

`c501c2d2b647bdc93be3c0102f36a84446767b20cbff123314173e04757a026d`,
Xid count zero, GPU use 14 MiB, no GPU/vLLM process, and port 8002 closed.
