# R1 K1A: QSA resident-set churn / selection-diff economics

## Status

Shadow-only planner experiment.

No KV is evicted, offloaded, staged in, or moved.

K1A exists because K0 answered only the first half of the KVMem question:

> Can QSA identify relevant old history?

K0 answer: **yes** on the deterministic 160K/240K needle suite.

K1A asks the second half:

> Across adjacent queries over the same long history, how much of a finite
> resident working set changes?

That determines whether a real CPU-tier implementation is likely to spend its
time retaining resident KV or repeatedly reloading most of the working set.

Therefore K1A does **not** revisit selector quality with more single-query

## Why not implement real KV offload immediately

A real bounded-KV path introduces several expensive and correctness-sensitive
components:

- CPU backing storage;
- logical-position -> resident-slot mapping;
- block-table remapping;
- stage-out / stage-in;
- retained-resident reuse;
- synchronization;
- recurrent/GDN checkpoint/replay;
- eventually MTP follower semantics.

Before paying that engineering cost we can estimate the central transfer
economics using QSA shadow selections alone.

KVMem's useful idea here is the **selection diff**:

`resident_t -> resident_(t+1)`

Only blocks in:
- `new - old` need stage-in;
- `old - new` need stage-out / release;
- `old & new` should remain resident.

K1A measures exactly these sets offline.

## Workload: same history, changing queries

Unlike K0, all turns in one context share byte-for-byte identical history token
IDs.

Contexts:
- 160K envelope
- 240K envelope

For each context the generator reserves 512 tokens for query room and creates a
fixed history containing six facts at approximately:

- 8%
- 22%
- 38%
- 55%
- 72%
- 88%

Turn sequence:

1. `ask_a`
2. `ask_b`
3. `ask_a_paraphrase`
4. `ask_c`
5. `ask_d_e`
6. `ask_a_repeat`

Turn 0 and turn 5 use the **exact same query token IDs**.

This gives two useful signals:
- semantic query switches test real resident-set churn;
- turn 0 vs turn 5 tests deterministic same-query replay.

## Runtime

Same research-only QSA shadow exporter as K0.

Required:
- eager execution;
- no MTP;
- prefix cache OFF;
- no production latency interpretation.

One engine per context.

Each turn:
- sends the same fixed history;
- changes only the final query;
- requests one output token;
- stores independent QSA shadow JSONL.

## Resident-set planner

For every turn the analyzer:

1. keeps only QSA selections generated by final-query rows;
2. removes any selected logical index at/after query start;
3. aggregates votes across observed QSA layers and query rows;
4. groups logical tokens into 128/256/512-token coarse blocks;
5. reserves mandatory sink + recent blocks;
6. fills the remaining finite budget by descending QSA vote count.

Budgets:
- 32K tokens
- 64K tokens

Mandatory within the same budget:
- first 512 tokens;
- latest 4096 historical tokens.

## Selection-diff metrics

For every adjacent pair of turns:

- retained blocks = old & new
- stage-in blocks = new - old
- stage-out blocks = old - new
- Jaccard similarity
- stage-in tokens
- stage-out tokens
- stage-in fraction of the fixed working-set budget

The same-query replay comparison additionally reports:
- turn0/turn5 Jaccard;
- exact set equality.

## Main-KV transfer-byte estimate

K1A estimates transfer bytes for the full-attention K/V cache only.

It deliberately does **not** include:
- GDN/recurrent state;
- PLE;
- model weights;
- QSA index metadata;
- allocator/bookkeeping overhead.

The analyzer reads the real model `config.json` and uses the observed number of
QSA/full-attention layers from shadow records.

Single-GPU BF16 estimate:

`bytes/token = qsa_layers * 2(K+V) * num_key_value_heads * head_dim * 2`

For each coarse block:

`bytes/block = bytes/token * block_size`

Each transition then reports:
- estimated stage-in bytes/GiB;
- estimated stage-out bytes/GiB.

These are transfer-volume estimates, not transfer-time measurements.

No PCIe bandwidth assumption is baked into the gate.

## Correctness signal retained

Every query still targets one or two known facts.

For every turn the analyzer checks:
- direct QSA token hit;
- target block recall inside each simulated working set.

A low-churn plan is useless if it drops the currently requested fact.

## Primary policy

Primary K1A policy:

- 256-token coarse blocks
- 64K resident budget

32K and 128/512-token variants remain sensitivity cells.

## Classification

K1A classification is descriptive, not production qualification.

### LOW_CHURN

All contexts collectively satisfy:

- median stage-in fraction <= 25%
- max stage-in fraction <= 50%
- same-query replay Jaccard >= 0.99
- target-fact recall >= 0.99

Interpretation:
resident reuse is strong enough that a straightforward selection-diff CPU-tier
prototype is justified.

### MODERATE_CHURN

If LOW_CHURN fails, but:

- median stage-in fraction <= 50%
- max stage-in fraction <= 75%
- same-query replay Jaccard >= 0.95
- target-fact recall >= 0.99

Interpretation:
K1 remains plausible, but the true prototype should measure H2D cost carefully
and may need a sticky/hysteretic resident planner.

### HIGH_CHURN_OR_UNSTABLE

Anything worse.

Interpretation:
do not immediately implement naive query-by-query eviction.

Next research step would be an offline sticky-residency planner:
- retain high-value old blocks across turns;
- spend only a fraction of the budget on query-specific replacements;
- re-evaluate recall/churn before real stage-in code.

## Important non-goals

K1A must not:

- evict or offload real KV;
- mutate vLLM block tables;
- allocate CPU KV backing;
- measure production TPOT;
- enable MTP;
- implement GDN replay;
- implement NVMe;
- add mean-K;
- change QSA scoring;
- merge into production.

## Decision after K1A

If LOW_CHURN:
- design real K1 target-only CPU-tier prototype;
- reuse vLLM native cache/block ownership;
- first implement selection-diff + retained-resident reuse;
- keep recurrent/GDN state out of the first attention-KV patch;
- still no MTP until target path is correct.

If MODERATE_CHURN:
- quantify real H2D stage-in on a minimal target-only prototype or add sticky
  planner simulation first, depending transfer volume.

If HIGH_CHURN_OR_UNSTABLE:
- do not write naive eviction code;
- solve planner stability in shadow mode first.
